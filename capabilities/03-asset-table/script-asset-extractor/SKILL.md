# 剧本资产表提取

输入一个标准剧本 docx，输出 Excel 资产表，包含 4 个 sheet：人物、场景、道具、场次总表。每个资产可以有多个状态，表里一行对应一个状态。

脚本目录：`.claude/skills/script-asset-extractor/scripts/`（下文用 `$S` 指代）
依赖：`python-docx==1.1.2`、`openpyxl==3.1.5`

## 正式输出

1. **`assets.json`** - 所有资产数据（人物、场景、道具及其状态）
2. **`<剧名>-资产表.xlsx`** - 最终交付的 Excel 表格

其他文件（`scenes.json` 等）为临时中间文件，保留在工作目录但不作为正式输出向下传递。

## 流程

### 1. 解析剧本

在剧本所在目录建一个工作目录 `<剧名>_资产提取/`，中间文件都放在里面。

```bash
python3 $S/parse_script.py <剧本.docx> <工作目录>/scenes.json
```

检查输出的集数、场次数和警告。有「未识别行」警告的话，说明剧本格式不标准，判断标准：

- **未识别行数量 > 总段落数的5%**，或 **连续10行以上无法解析**：停止，告诉用户剧本格式有严重问题，需要检查修正
- 否则，只要集数、场次数、人物行能正常提取（不是0集0场），可以继续——未识别行通常是【闪回】【闪出】、卡点标记、格式说明之类的非核心内容，不影响资产提取

### 2. 提取资产

开始前先读 `references/asset_schema.md`，判定规则和 JSON 格式都在里面。

**单人单线程时**：按集数分批读，每次 5 集：

```bash
python3 $S/show_episodes.py <工作目录>/scenes.json 1 5
```

**剧集较多、想用 subagent 并行加速时**：不要按集数切分批次给不同 agent——人物的状态判断依赖该人物在全剧的完整换装轨迹（比如"这一集的特殊造型后面还会不会再出现"，只看局部集数看不出来），按集数切会导致同一个人物的状态被不同 agent 各看一段、谁都看不到全局，这正是之前漏掉状态、事后要靠整剧重新核对才补上的根源。

正确的并行轴是**按资产类型分工**，每个 subagent 都拿到完整剧本（全部 `show_episodes.py` 输出或完整 `scenes.json`），只负责提取其中一类资产：

- 一个 agent 专门提取人物（如果人物多，可以再按主角/配角/群演细分成多个 agent，但每个 agent 负责的人物必须覆盖该人物在全剧的所有出场，不能按集数再切一刀）
- 一个 agent 专门提取场景（含主子场景层级判断）
- 一个 agent 专门提取道具

**派发给 subagent 的任务说明里必须直接贴出目标 JSON 骨架**，不能只说"参照 `references/asset_schema.md`"——subagent 读完规则文档后仍然经常会自创一套顶层结构（比如把 `characters`/`scenes`/`props` 三段式换成 `{locations, props, effects, costumes}` 或塞进 `special_effects`/`vehicles`/`notes` 这类文档里完全没有的字段）。任务说明至少要包含：

```json
// 人物 agent 必须只返回这个形状，顶层只有一个 "characters" 数组，不能新增别的顶层字段
{"characters": [ {"id": "CHR-001", "name": "...", "aliases": [], "role": "...", "description": "...", "note": "", "states": [...]} ]}
```

```json
// 场景 agent 必须只返回这个形状，顶层只有一个 "scenes" 数组
{"scenes": [ {"id": "SCN-001", "name": "...", "aliases": [], "int_ext": "...", "times": [...], "description": "...", "note": "", "subscenes": [...], "states": [...]} ]}
```

```json
// 道具 agent 必须只返回这个形状，顶层只有一个 "props" 数组
{"props": [ {"id": "PRP-001", "name": "...", "aliases": [], "owner": "...", "description": "...", "note": "", "states": [...]} ]}
```

明确告诉 subagent：**只能在给定骨架里填充数组元素，不能新增、删除或重命名顶层字段，不能把"特效""服装细节""载具"等单独建类**（特效和持续性外观变化的关系见下面"动作原文 vs 外观描述"一节；载具、服装按人物状态或道具收录，不单独成类）。收到 subagent 结果后，第一步先检查顶层字段名是否就是这三个数组之一，字段名不对直接打回重做，不要试图在合并时手工把它掰成标准结构——那样内容本身的提取质量也无法信任，必须重新做。

**subagent 输出文件名约定**：
- 人物 agent 输出到 `<工作目录>/characters.json`
- 场景 agent 输出到 `<工作目录>/scenes_extracted.json`（避开 `scenes.json` 这个已被 parse_script 占用的名字）
- 道具 agent 输出到 `<工作目录>/props.json`

每个 subagent 各自产出一份自己负责那部分的 JSON 片段（只含一个顶层数组），**不自己跑 `--check`**，由主 agent 统一合并后再校验——分散校验既浪费时间，也可能出现各 agent 自查通过但合在一起互相矛盾（比如人物 agent 和场景 agent 对同一个场次的归属理解不一致）。

无论单线程还是并行，提取时都要遵守：

- 已有资产：在对应状态的 `scenes` 里追加场次；出现换装或外观大变化时，新增一个状态
- 新资产：按编号规则追加（并行提取时，各 agent 的编号段提前分配好范围，如人物 CHR-001~CHR-050、场景 SCN-001~SCN-050，避免合并时 ID 冲突）
- **角色分类规则**：
  - **有台词的角色必须归类为"配角"**，即使角色名称看起来像群演（如"侍从1"、"使节1"、"守卫2"），只要在剧本中有对白，就不能标记为"群演"
  - **"群演"仅用于无台词但有连续性出场的群体性角色**（如"黑甲守卫"、"侍女"、"贵族宾客"等）
  - 提取前必须先检查剧本中的台词，识别哪些看似群演的角色实际上有对白
- 一直跟踪每个人物「当前穿的是哪一套」，后续场次没有换装描写就沿用当前状态
- 每个资产至少有一个常态；拆出新状态时，`evidence` 必须引用原文中触发换装或持续性外观变化的短句，状态名、描述和场次必须与原文一致。仅有婚礼、寝宫、下雨等场景信息，不能推断出礼服、睡袍、雨衣等新状态；原文没有描写变化时，沿用当前状态，并把可能需要补充设计的场次写入 `note` 待人工确认。不得凭空新增资产或关键陈设（例如原文只写「黑曜大厅」，不能编出「龙骨王座」）。
- **合理推断只用于补充已有资产或已有状态的视觉细节，不作为新增状态的依据。** 描述中补充的年龄范围、材质等未明示细节，必须在 `note` 中列出推断内容、依据和适用范围，交给人工确认；无法合理判断的细节写「剧本未说明，待设计确认」。已明确出现且没有后续变化描写的造型或布置可以延续使用，不属于新增状态。完整规则见 `references/asset_schema.md`。
- 给一个状态加场次号之前，确认这一场的「人物：」行里确实写了这个人物的名字（或别名）。不要凑数、不要把相邻场次的状态延续到这人其实没出场的那一场

单线程按集数分批时，不要一次读完全剧再提取，容易漏掉场次和状态切换。

### 2.5 回查原文找证据（辅助工具）

`enrich_descriptions.py` 能按资产名/别名把剧本里所有提到它的动作行拉出来，适合验证或补全 `evidence`、核实状态是否编造：

```bash
python3 $S/enrich_descriptions.py <工作目录>/scenes.json <工作目录>/assets.json
```

输出是每个道具/场景在剧本里被提及的原文片段（不含人物，人物的回查直接用 `show_episodes.py` 按集看原文即可）。这不是必须每次都跑的步骤，而是在以下情况下用来核实：

- 第 4 步生成完 Excel 后抽查某个状态时，想确认 `evidence` 没写错
- `--check` 报了道具归属警告，需要回查原文判断是否真的有问题
- 对某个状态该不该拆、场次该归哪个状态拿不准时

### 2.6 合并 subagent 结果（仅并行提取时需要）

从各 subagent 的输出文件（`characters.json`/`scenes_extracted.json`/`props.json`）读取数组，拼成最终的 `<工作目录>/assets.json`：

```json
{
  "characters": [...],  // 从 characters.json 读取
  "scenes": [...],      // 从 scenes_extracted.json 读取
  "props": [...]        // 从 props.json 读取
}
```

拼的时候检查：

- ID 段有没有按分配范围来，有没有冲突
- 场景 agent 对某场次的子场景归属，和人物 agent 对同一场次的理解是否一致（例如人物 agent 可能把某人分到了"8-3"，但场景 agent 没把"8-3"纳入任何子场景的 `scenes`）
- 不要假设每个 subagent 都做对了——合并只是把数据拼起来，真正的核实在下一步统一做，合并这一步本身不是校验

合并完成后，**主 agent 必须亲自做一次第 4 步后半段讲的"回查原文抽查主要人物"**，不能假设分给 subagent 的任务就不需要复核了。分工并行换来的是省时间，不是省掉质量把关这道工序——上次漏掉凯尔的龙形状态，就是因为没人在提取之后做这步复核。

### 3. 校验并补漏

```bash
python3 $S/build_xlsx.py <工作目录>/scenes.json <工作目录>/assets.json --check
```

- 错误（ID 重复、引用不存在的场次、资产没有状态）必须修
- 警告「人物行中的某某没有对应资产」：补资产或补 `aliases`
- 警告「某某出场但没有分配到任何状态」：回到那一场的原文，把人物分到正确的状态里
- 警告「某某的状态 XX 引用了此场次，但剧本人物行里没有某某出场」：说明状态数据手工编辑或合并时写错了场次号，去对应人物的那个状态里把这个场次删掉，再看它本该属于哪个状态
- 警告「道具某某的归属人物某某未在此场次人物行中出现」：这是弱提示，不一定是错（道具可能被别人临时拿着），但要回查原文确认场次号没写错，确认没问题后这条警告可以忽略
- 反复执行，直到没有错误，警告也都处理完或确认可以忽略

这一步做的是**双向校验**：不仅要保证人物行出场的都分配了状态（正向），还要保证分配进状态的场次该人物确实出场（反向）。只做正向校验会漏掉"把场次塞错了状态/塞给了不存在的出场"这类问题——合并资产、批量改场次号时最容易出这种错，必须两个方向都跑一遍再确认没有警告。

道具没有「人物行」那种结构化字段可以强校验，`--check` 对道具只能做弱提示（归属人物是否在场）。道具的 `evidence`/`scenes` 本质上和人物状态一样是手工填写的，同样可能写错场次、编造描述，程序查不出来的部分要靠人工回查，不能因为"道具没报警告"就当它一定没问题。

**禁止在第 3 步有任何错误或警告的情况下跳到第 4 步生成 Excel。** `--check` 必须显示「错误 0 条，警告 0 条」才能继续；无法消除的警告要先跟用户确认是否可以忽略，不能自行默认忽略后直接生成。

### 4. 生成 Excel

```bash
python3 $S/build_xlsx.py <工作目录>/scenes.json <工作目录>/assets.json <剧本目录>/<剧名>-资产表.xlsx
```

生成之后，**不代表校验就此结束**。还要用剧本原文抽查几个有多个状态的主要人物（尤其是男女主角）：对每个状态，找到它名字/描述对应的原文依据，确认原文写的场次和状态归属一致，而不是状态名和场次号对不上（例如把"龙形显现"这种描述塞进了实际是"婚礼"的场次里）。这种错误 `--check` 的程序校验查不出来，只能靠回查原文发现。

如果是第 2.6 步合并多个 subagent 结果得到的 assets.json，抽查范围要加上场景的主子结构：挑几个有子场景的主场景，确认 `int_ext`/`times` 字段没被漏写（场景 agent 容易漏这两个字段，且 `--check` 现在会对此报错，但要确认值本身填对了，不只是"有值"）。

### 5. 汇报

用几句话说明以下内容：

- 人物、场景、道具各有多少个资产、多少个状态
- 合并了哪些同名异称
- 待人工确认的条目（疑似同一道具、拿不准是否该拆状态的变化、剧本没写但常理上可能该有专属造型的场次——这类都写进了对应状态的 `note`，汇报时要点出来，不要让它们被默认忽略）
- `--check` 的结果（确认是 0 错误 0 警告，不要略过不提）

不要把整张表复述一遍。

**交付物**：

- `<工作目录>/assets.json` - 资产数据
- `<剧本目录>/<剧名>-资产表.xlsx` - Excel 表格

（`scenes.json` 等中间文件保留在工作目录，但不向用户提及或传递）

## 状态规则摘要

只有换了一套衣服，或者外表有很大变化，才拆出新状态。表情、动作、日夜、灯光都不算。完整规则见 `references/asset_schema.md`。
